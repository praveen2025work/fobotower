The problem

Most control and operations work is the same job in different clothes.

Each team rebuilds it by hand, in spreadsheets and email, with its own version of four-eyes, authority limits and audit. Every auditor checks it differently. A model can do the gathering and first reasoning, but on its own it brings ungrounded figures, unauthorised decisions and writes nobody approved.

  • 01 · arrive

    A list of items

    Breaks, exceptions, alerts, complaints, journals, samples.

  • 02 · gather

    Data from 3 to 6 systems

    Ledgers, trade stores, payment engines, CRM, documents.

  • 03 · explain

    Work out what happened

    Match, recompute, compare to history, read the evidence.

  • 04 · decide

    The right person decides

    Within their authority, with a second pair of eyes.

  • 05 · act

    Write back the outcome

    Post, repair, refund, notify, raise a ticket.

How a case runs

Every capability follows the same governed path.

A team describes its work as a capability: what a case is, where the items come from, the steps, who decides and what is written back. Helix runs it the same way every time.

1

Get the items

Load from a system or match two; open by hand, on a schedule or on an event.

2

Prepare

Rates, limits, bands, clocks, samples, timelines: configurable steps.

3

Propose

Rules first, then the model with read-only tools, then a person. Every figure checked.

4

People decide

Authority tiers, reserved decisions, checklists, questions to other teams.

5

Record

Decisions kept and learned from; tickets raised; re-checked on the next run.

6

Release, write back

A second person releases; each write happens exactly once.

One gateway under every stepentitlementsdata scope per usermasking before any modelan audit row per call

A tollgate can stop the run before any step for a named person to approve the work so far. Nothing reaches a system of record until a second person, who did not review the case, releases it.

Building blocks

44 blocks, no team-specific code.

Thresholds are named policy values. Logic is expressions. Anything else is the team's own service, called through the gateway. A new step type is added once, through a small SDK, and every team can use it.

Controls built in

A team cannot configure these away.

  1. People decide

    The model proposes, a person decides. When nothing settles a group, it goes to a person, not a guess.

  2. Authority

    Tiers by amount, risk or verdict set who may approve and how many different people must. Held in Helix or read from the bank's delegated-authority system.

  3. Reserved decisions

    Credit, sanctions, AML, redress above a limit, payment release: only named roles decide, never in bulk. A model proposal there is withheld.

  4. Segregation of duties

    The opener may be barred from signing off. Whoever releases a write-back did not review the case.

  5. No silent writes

    Only tools marked as writes, only after approval, each write idempotent; the ledger's own check runs first.

  6. Grounded figures

    Every figure traced to the data. Values read from documents must appear in them; low-confidence or regulated values go to a person.

  7. Nothing dropped

    Items set aside stay on the case with the reason. Samples keep their seed.

  8. Data protection

    Entitlements and data scope per user, masking before any model sees a field, an audit row for every call.

  9. Change control

    Every configuration change checked as it is made and approved by a second owner. A case keeps the version it ran on.

  10. Model risk

    Eval sets and shadow runs before go-live, cost limits, off switches, instructions versioned and approved.

Adopt it

From a team's process to a live capability.

A new use case needs configuration and, at most, a connector to each system it reads or writes. The platform team is needed only for a new connector or a new step type.

  1. Describe the work

    Answer guided questions, paste a requirements document, or start from a template.

  2. Connect the systems

    Each system is an MCP connector, onboarded once, tools marked read or write and scoped.

  3. Configure the steps

    Reviewers, authority, reserved decisions, tollgates, what is written back and who releases it.

  4. Approve the version

    A second owner approves. Until then nothing runs on it.

  5. Prove it

    Eval sets and shadow runs against past cases before go-live.

  6. Run it

    Cases open by hand, on a schedule or on another system's event.

  7. Improve it

    Recurring items, what nothing explained, judgement calls ready to become rules.

  8. Add team groups

    Other desks run the same capability with their own settings, within what it allows.

Fit

Where Helix fits, and where it does not.

A strong fit

  • Work that arrives as a list of items, each needing an investigation and an accountable decision.
  • Data spread over several systems that someone gathers by hand today.
  • Controls that matter: four-eyes, authority limits, evidence for audit.
  • Repeating work, daily, monthly or per event, where yesterday's decisions inform today's.

Not what it is for

  • Not a system of record. Ledgers, payment engines and KYC systems keep their data and controls.
  • Not an autonomous decision-maker. It never clears a screening hit or releases a payment.
  • Not real-time. Cases take seconds to minutes; in-flight checks belong in the transaction path.
  • Not forms and routing alone. Work with no investigation is better served elsewhere.
