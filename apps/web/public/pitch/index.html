The problem

Most of Finance's control work is the same job in different clothes.

A FOBO break, a cash rec difference, a P&L variance or a month-end accrual all follow the same five moves. Today each team runs them by hand, in spreadsheets and email.

A list arrives

Breaks, exceptions, alerts, complaints, journals, samples.

Data from 3–6 systems

Gathered by hand into a workbook.

Work out why

Match, recompute, compare to history.

Someone decides

Within authority, with four eyes.

Write it back

Post, repair, refund, notify, raise a ticket.

SlowHours of gathering before any thinking starts, in every team, every cycle.
Scattered evidenceFour-eyes, limits and audit trails rebuilt per team, checked differently by each auditor.
Risky with a model aloneUngrounded figures, decisions without authority, writes nobody approved.
How it works

Every capability follows the same governed path.

A team describes its work as a capability: what a case is, where the items come from, the steps, who decides and what is written back. Agent One Finance runs it the same way every time.

Make it work

What it takes to run this for real.

The platform, the controls and the console are built. A team brings four things: its systems, its configuration, its people and a proving run.

1 · connect the systems

The ledger and the authority matrix, as connectors

Each system is an MCP connector, onboarded once. Reads and writes are marked; a write runs only after release.

journals.grnireadgoods received not invoiced, per entity and period
journals.period_status, chart_of_accountsreadis the period open; the postable accounts
authority.delegated_authorityreadthe bank's own matrix: amount bands, roles, approvals
journals.validate_journal, post_journalwritethe ledger's check first, then posting, each journal once
2 · configure the capability

About 100 lines, edited in the console

Steps, thresholds and roles. No code. Every change is checked as it is made and approved by a second owner.

steps: [load, open_period, chart, authority, accrual, material,
        group, reason, entries, draft, validate, review, record, post]
pause_before: [review, post]
policy: { materiality: 5000 GBP }
review:
  roles: [FIN_PREPARER, FIN_REVIEWER]
  authority_dataset: authority   # the bank's matrix stays the source
post: { approver_roles: [FIN_CONTROLLER] }  # never a reviewer
3 · name the people

Roles from your entitlement system

PreparersFIN_PREPARERopen the run and see everything; not above the matrix
ReviewersFIN_REVIEWERapprove within the matrix; two different reviewers over 250k
Financial controllerFIN_CONTROLLERreleases the journals to the ledger; never a reviewer of the case
Two ownerscapability ownerschange the configuration; each change approved by the other
4 · prove it, then run it

Run it locally today; shadow-run before go-live

The full build runs on a laptop with stub systems and no model. In the office, connectors point at the real systems, and an eval set checks the proposals on past periods.

    Adopt it

    From a team's process to a live capability.

    A new use case needs configuration and, at most, a connector per system. The platform team is needed only for a new connector or a new step type.

    1. Describe the work

      Guided questions, a requirements document, or a template.

    2. Connect the systems

      MCP connectors, onboarded once, read or write, scoped.

    3. Configure the steps

      Reviewers, authority, reserved decisions, tollgates, write-back.

    4. Approve the version

      A second owner approves; until then nothing runs on it.

    5. Prove it

      Eval sets and shadow runs against past cases.

    6. Run it

      By hand, on a schedule or on another system's event.

    7. Improve it

      Recurring items, the unexplained, judgement calls ready to become rules.

    8. Add team groups

      Other desks run it with their own settings, within what it allows.

    Fit

    Where Agent One Finance fits, and where it does not.

    A strong fit

    • Work that arrives as a list of items, each needing an investigation and an accountable decision.
    • Data spread over several systems that someone gathers by hand today.
    • Controls that matter: four-eyes, authority limits, evidence for audit.
    • Repeating work, daily, monthly or per event, where yesterday's decisions inform today's.

    Not what it is for

    • Not a system of record. Ledgers, payment engines and KYC systems keep their data and controls.
    • Not an autonomous decision-maker. It never clears a screening hit or releases a payment.
    • Not real-time. Cases take seconds to minutes; in-flight checks belong in the transaction path.
    • Not forms and routing alone. Work with no investigation is better served elsewhere.
