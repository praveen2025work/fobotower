Purpose and scope

ARB and CDO are asked to approve one thing: running FOBO break investigation on Agent One Finance, a shared, governed AI framework inside the Product Control (PC) reporting application. FOBO becomes configuration on that framework, not a separate application.

In scope

  • The FOBO use case only: breaks that Masterbook Rec has already reconciled between CATS (front office) and MOTIF (back office), for the Prime and Rates books.

  • Agent One Finance's containers and components as they serve FOBO.

  • The data FOBO reads, keeps and sends, and how the model is allowed to use it.

Out of scope

  • Other capabilities on the framework (cash, variance, accruals and others). Each comes to ARB separately as configuration on this approved base.

  • Changes to Masterbook Rec, CATS, MOTIF or FAS themselves. Agent One Finance only reads from them through their MCP servers.

Assumptions to confirm. Element names follow the office naming. The roles of Finance Portal, Workspaces and FAS below are a first reading. The architect team should correct them before submission (see Open questions).

C4 level 1: system context

Agent One Finance sits inside the PC reporting application beside Masterbook Rec, Finance Portal, Workspaces and FAS. It is the one governed AI component they share, and FOBO is its first use case.

Masterbook Rec starts each run with its end-of-day event. Agent One Finance reads Masterbook Rec, MOTIF and CATS, asks Agent One's model only for judgement, and raises tickets after a controller decides. FAS (dashed) has no direct link in this release.

C4 level 2: containers

Agent One Finance is five containers and its configuration files. The MCP gateway is the only way out to bank systems; the model is reached only through Agent One.

The API and workflow engine run every FOBO case. The gateway checks each call against the allow-list and the user's books, masks protected fields and writes an audit row before it calls Masterbook Rec, MOTIF, CATS or Ticketing. FOBO's configuration lives in Git and becomes an approved version in the case store, so a case always runs on a known version.

C4 level 3: components

The API container holds eleven components. The workflow engine is the only one that runs steps, in the order the capability's configuration sets. Every call to a bank system goes through the MCP gateway, and only the reasoner talks to the model, through Agent One.

The engine's line on the left is one bus: it calls each component in turn. Components on the right side of the bus read or write through the gateway; those on the left work only on the case's own data.

For CDO: data, lineage and the model

FOBO reads trading and reconciliation data classified confidential. It holds no client personal data. Every read is logged with who, which tool, the arguments and the row count. The model is reached only through Agent One, the office's approved model access; where the model runs and what it retains is covered by Agent One's own approval.

Lineage. Every figure on a break carries its source: the tool and step that read it, shown under Data used on each case. Every figure the model writes must appear in data it read; the validate gate sends anything else to a person. Each decision records the configuration version that produced it.

The model and data

  • The model sees one group of breaks at a time, only after a controller passes the checkpoint, and only for judgement categories. The rules settle the rest with no model call (3 of 6 groups in the reference run).

  • It can call only four read tools, listed in the FOBO configuration. Each call goes through the gateway: allow-list, book scope, masking, audit.

  • Fields marked for protection in governance.yaml are masked or pseudonymised before the model sees them, and restored after. FOBO data carries none today; the controls apply automatically if a source adds counterparty identity.

  • The model never writes to a bank system. Tickets are raised by Agent One Finance after a person decides.

Data quality. A missing field makes a validation test "not run", never a pass, so a gap in the feed shows up as more breaks going to a person. The Data and parameters panel lists every field each check and test reads, and its source.

Architecture decisions, risks and open questions

Decisions

#DecisionWhyAlternative rejected
AD-1FOBO is configuration on a shared framework, not its own applicationOne engine, one set of controls and one approval for every Finance use case; FOBO Rates and future teams reuse itA FOBO-only application with its own orchestrator, rules code and console
AD-2Masterbook Rec stays the system that reconciles; Agent One Finance never re-matches CATS to MOTIFOne source of truth for breaks; no second reconciliation to reconcileMatching CATS to MOTIF again inside Agent One Finance
AD-3Mechanical rules run as code from configuration; the model handles judgement onlyThe same input gives the same answer; rules cannot be skipped; lower model cost and riskThe whole skill given to the model in a session
AD-4Every system call goes through one gateway (MCP)One place for allow-list, book scope, masking and auditSystems called directly by steps or by the model
AD-5Model access through Agent One's Agent SDK wrapper, behind an adapterReuses the office's approved model access; the model can change without changing FOBOA direct model API from Agent One Finance
AD-6No write-back to FAS in this releaseKeeps the first approval read-only; Operations books from the ticketPosting adjustments directly

Risks

RiskMitigation
A model proposal is wrongIt is only a proposal: guards apply after it, figures must trace to data, a controller decides every group, and eval sets replay past cases before changes
A Masterbook Rec or MOTIF field is missingThe test that needs it is "not run"; the break goes to a person; the data contract lists every field
Category differs from the old FOBO runParity script compares category, side and verdict for every break; differences are logged and decided by Product Control before go-live
Cross-book data reaches a user scoped to some booksThe cross-book step keeps only a count on the case; names and figures of other books are not stored
Framework change affects FOBOA case keeps its configuration version; changes are approved by a second owner and replayed first

Open questions for the architect team

  1. Confirm the roles of Finance Portal, Workspaces and FAS, and whether Workspaces should receive the evidence pack automatically.

  2. Confirm owners for each external system in the catalogue.

  3. Masterbook Rec: can it send the end-of-day event, and offer break_history_book and breaks_all?

  4. Agent One: data retention and residency for model calls, to cite in the CDO pack.

  5. Hosting: the PC reporting application's platform, availability target and database recovery.

  6. When should a write-back to FAS come for approval?
