FOBO runs on Agent One Finance (AOF) as one Helix agent with a configuration per named P&L (NPL). MB Rec in PC Ramp tells AOF when an NPL is ready. AOF reads the CATS and MOTIF data through MB Rec's MCP server, a FOBO controller decides, and approved adjustments reach MOTIF through FAS's MCP server.

The design in ten points

Every point of the agreed design fits AOF as built. Three need work outside AOF: the notification from MB Rec, the MCP tools on MB Rec and FAS, and the shape of PC Ramp's entitlement answer.

C4 level 1: system context

AOF sits between PC Ramp and FAS. MB Rec starts each task, FOBO controllers decide, and the only write to a bank system goes through FAS.

CATS and MOTIF data reach AOF only through MB Rec's MCP server. MOTIF is read directly only by the Balance rec agent.

C4 level 2: containers

Inside AOF, the API and Helix engine run every task. The MCP gateway is the only way out to bank systems. Users reach AOF only through Agent One, and the model only through Agent One's model access.

Helix agents and NPL configs

One Helix agent for FOBO holds the steps, gates and sign-off. Each NPL is a config on it with its own rules, thresholds, owners and reviewers. MB Rec's notification names the NPL, and the task runs on that NPL's config.

A new NPL is a new config, approved by two owners; no code changes. A separate agent per NPL is needed only if an NPL needs different steps or gates. Balance rec is its own agent on the same engine.

Dynamic view: one NPL run

One task covers one NPL and one COB. Steps 3 and 4 use no model. The model is used only at step 7, only for what the checks could not explain, and only after a controller passes the tollgate at step 6.

For CDO: data flows, lineage and the model

FOBO reads trading and reconciliation data classified confidential, and holds no client personal data. AOF reads it only through MCP servers, logs every call with who, which tool, the arguments and the row count, and writes to a bank system only through FAS, after two people.

Lineage. Every figure on a break carries the MCP tool and step that read it, shown under Data used on the task. Every figure the model writes must appear in data the task read; the validate gate sends anything else to a person. Each decision and each posting records the config version that produced it.

The model and data

  • The model sees one group of breaks at a time, only after a controller passes the tollgate, and only what the checks could not settle.
  • It can call only the read tools the NPL config lists, each through the MCP gateway: allow-list, NPL scope, masking, audit.
  • It never writes to a bank system. Postings go to FAS only from the post step, after sign-off and release.

Data quality. A missing field makes a validation test "not run", never a pass, so a gap in MB Rec's data shows as more breaks going to a person.

For ARB: controls and non-functional requirements

The controls below are enforced in code and configuration, not by the model's instructions, and each has an automated test.

Risks

RiskMitigation

Open questions

  1. MB Rec's notification: does it carry the agent and NPL config as well as the NPL and COB? Today AOF needs the config named; mapping NPL to config inside AOF is a small addition.
  2. MB Rec's MCP server: tools for an NPL's breaks with a stable break id, each master book's status, and the FO/BO data per break.
  3. FAS's MCP server: the adjustment's fields, its validation call, and how a posting is reversed.
  4. PC Ramp's entitlement URL: does it return each user's roles and NPLs, or answer yes or no per user and NPL? The second needs a small adapter.
  5. Who releases postings: another FOBO controller, or a separate role?
  6. Balance rec: which MOTIF data it reads, and who signs it off.
  7. Agent One: data retention and residency for model calls, for the CDO pack.
  8. Owners for MB Rec, PC Ramp entitlements, FAS and MOTIF.
