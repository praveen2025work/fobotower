AOF in Plain Words

Agent One Finance · FOBO

AOF is a fast new team member that follows your checklist and never acts alone.

Every morning it picks up the work, pulls the facts from the bank's systems, sorts out what the team's rules can settle, writes up the rest, and waits for a FOBO controller to decide. Nothing changes in any bank system until a controller approves and a second person releases it.

The use case

One morning for a FOBO controller

An example of the target morning. The counts are illustrative; the 120.00 SOFR future break is a real case from the demo. Posting through FAS is being added in the plan.

  1. 06:30
    AOF

    MB Rec finishes reconciling book PRIME-MB-01 for 8 Oct. AOF opens a case on its own and reads the 12 open breaks.

  2. 06:31
    AOF

    It gathers the evidence: each break's last five days in MB Rec, and the book's positions and booking events in MOTIF.

  3. 06:33
    AOF

    It runs the known checks, plain arithmetic with no AI, then applies the FOBO playbook:

    5timing differences that will clear tomorrow (watch, no action)2equal and opposite: booked to the wrong instrument (to the desk)1a split booking whose pieces add up to the break (explained)1SOFR future, MTM difference of 120.00, inside the auto-adjust limit (propose an adjustment)3not settled by any rule (need judgement)
  4. 07:45
    FOBO controller

    First stop. Frank checks these are today's breaks and the playbook's sorting is right, and adds what the desk told him. Only then is the AI asked anything.

  5. 07:47
    AOF

    For the 3 open breaks, the AI reads the evidence and writes why it thinks each happened. Every figure it quotes is checked against the source; a proposal with a figure that cannot be traced goes to a person instead.

  6. 08:00
    FOBO controller

    Second stop. Frank opens his inbox: 5 groups to decide, each with its evidence, instead of 12 raw breaks. He approves 4 and rejects 1 with a comment, working from the evidence instead of starting each break from scratch.

  7. 08:15
    Second controller

    A different controller releases the 120.00 adjustment. FAS posts it to MOTIF once, and AOF reads it back to confirm it landed.

  8. Next day
    AOF

    It checks whether the 5 timing differences cleared, and flags any that did not.

The steps

What each step does, and why they are in this order

A capability is an assembly line. Each step takes what the earlier steps produced and adds one thing. That is how steps relate: a step can only use what came before it. The configuration screen checks this for you and refuses a step that needs something nothing earlier made.

For the tech team: how a capability is written

A capability is a YAML file. The steps are a list. Built-in steps need no settings; configurable steps say what they read and produce. This is the FOBO file, shortened:

id: break.investigation
items:
  load: { tool: mbrec.breaks, args: { book: $case.book, cob: $case.cob } }
steps: [load, enrich, history, events, bo_positions, offsets, split_bookings,
        systemic, near_refs, trend, unusual, resolve, classify, group,
        reason, draft, validate, review, record]
step_settings:
  history:
    type: dataset
    with: { name: history, tool: mbrec.break_history_book, args: { book: $case.book, cob: $case.cob } }
  offsets:
    type: offsets
    with: { amount: difference, within: [book], tolerance: 0.01 }
pause_before: [reason, review]        # the two stops for a person
review: { roles: [FOBO_CONTROLLER], require_comment: [reject, escalated] }

The engine refuses a capability that breaks the rules: validate → review → record must all be there in that order, a step may only use data an earlier step produced, at most one posting step comes after record, and the run must pause before it.

Connections

How AOF gets data: MCP in plain words

Each bank system offers AOF a short menu of questions it will answer, through a standard plug called MCP. AOF keeps an allow-list: which systems, which questions, and whether a question only reads or also writes. A step asks a question by name, such as mbrec.breaks or motif.positions.

MB Recbreaks · break history · book status
MOTIFpositions · booking events · break snapshots
Reference datainstruments · corporate actions
AOF gatewaychecks every question against the person's books
Documentsread PDF and Excel · write reports
FASpost adjustment to MOTIF · write · release step only
Messages and ticketsask the desk · raise a ticket · after a person approves
Three rules on every call

1. Only questions on the allow-list can be asked. 2. Every question carries who is asking, and the gateway checks that person may see that book. 3. A question that writes is never given to the AI; only the release step can use it, and each write happens once.

For the tech team: connecting a new system
  1. The system's team publishes an MCP server for it (http).
  2. The AOF team adds it to config/agent-one-finance/connectors.yaml: its address, the allowed tools, which argument carries the data scope, and access: write on any tool that changes something.
  3. A step uses it by name: tool: motif.positions. The AI can only use tools listed for it in reasoning.tools.
  4. Test against the stub first, then switch the entry to the real address. No code change.
connectors:
  motif:
    name: MOTIF
    transport: http
    url: https://motif-mcp.internal/mcp
    headers_env: { Authorization: MOTIF_MCP_AUTH }   # value from a secret
    tools:
      positions:      { scope: { arg: book, key: book } }
      booking_events: { scope: { arg: book, key: book } }
  fas:
    tools:
      post_adjustment:
        access: write                 # never offered to the AI; release step only
        idempotency_arg: idempotency_key
        scope: { arg: book, key: book }

Posting

Can AOF post at each step, or only at the end?

Only at the end, once, and only after two people. Every step before the decision only reads and proposes. This is deliberate: nothing reaches MOTIF that a FOBO controller did not approve and a second person did not release, and the audit trail shows both names.

Steps 1–5Read, check, propose. No writes.
ReviewA FOBO controller approves the adjustment.
ReleaseA different person releases it.
PostFAS posts it to MOTIF once, then AOF confirms it landed.
If you need…Do this
To post in stages (for example each book, or each group, as soon as it is decided)Split the work into child cases: a parent case opens one child per book or group. Each child has its own review, release and posting, so each part posts when it is ready.
To ask the desk or a trader something in the middleAn outreach step sends the question after a person approves sending it. The answer comes back into the case. This is a message, not a posting.
To raise a ticket for another teamThe record step raises it after review, one ticket per case and group, however often it is retried.
A report or evidence packA report step after the decision writes a PDF. It can sit next to the posting.

Saying it

How to explain AOF to anyone

To a business person, in 30 seconds

"Every morning our FOBO controllers investigate breaks by hand. AOF does the legwork first: it pulls the facts, settles what our rules can settle, and writes up the rest. The controller reviews groups with the evidence attached and decides. Nothing is posted until a second person releases it."

To a tech person, in 2 minutes

"It is a workflow engine for governed AI. A capability is a YAML checklist of steps; each step reads what earlier steps produced. Data comes in through MCP servers on an allow-list, checked against the user's entitlements on every call. Rules run before the model, the model sees only allowed tools, every figure is validated against source, and there are three fixed gates. Writes happen once, after review and a second person's release."
