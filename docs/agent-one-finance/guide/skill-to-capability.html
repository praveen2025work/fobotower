Skill to Capability

Agent One Finance · building capabilities

How the FOBO skill became a capability, and how to build the next one

A skill document is written for a person. AOF needs the same knowledge in four different places, because each kind of sentence is run differently: by code, by the AI, by a person, or not yet at all. This page shows where every section of the FOBO Investigation Skill v1.0 went, then the steps to do the same for a new skill, with all data coming from MCP tool calls.

The basis

Sort every sentence of the skill into one of four kinds

This one sorting decides everything else. Read the skill line by line and ask: can this be checked by a formula on the data? If yes, it is a rule. If it needs reading and weighing evidence, it is judgement. If it says a person must do or confirm something, it is a people step. If it names a number nobody has agreed yet, it is a parameter.

1. Mechanical rulesFO-2: yesterday close price = today open priceRun as code on every break, before any AI. Same answer every time.→ the playbook: checks, tests, categories, verdict table, guards
2. JudgementComplex corporate actions, novel events, multiple root causesThe AI reads the evidence the tools return and writes hypotheses, never an assertion.→ AI instructions, its tools, its output sections, specialists
3. PeopleMark it for SME review rather than asserting itA stop where a person confirms, decides, answers or releases.→ stops, review, checklist, questions to the desk, tickets
4. Numbers not agreed yetMateriality threshold: TO BE CONFIRMEDLeft empty on purpose. A rule that needs an empty number does not run and says so (rule P1).→ policy values, empty until Product Control confirms

Two files

The capability is the shape; the group is the team's rules

Capability: the same for every team

  • What one case is: key: [book, cob]
  • How the items load: tool: mbrec.breaks
  • The step list, the stops and the three gates
  • Who may review
  • What a team is allowed to change (configurable)

Group: one team's version

  • When cases open (MB Rec's end-of-day event) and when they are due
  • Extra data per break: enrich
  • The playbook: checks, tests, categories, verdicts, guards
  • Thresholds (policy), AI instructions, tools, output sections
  • Questions to the desk, tickets, the review checklist

FOBO Prime and FOBO Rates are two groups on one capability. A third team reuses the shape and brings its own rules.

Data from MCP

Every field a rule reads must arrive from a tool

A test like FO-2 reads two fields on the break: fo_prev_close_price and fo_open_price. Those fields only exist if a step brought them in. There are four ways in, all through MCP tool calls:

Way inWhat it doesFOBO example
loadThe items themselves, one row eachmbrec.breaks: the open breaks for the book and date
enrichJoins more fields onto each item by keymotif.break_snapshots, by instrument: the dated FO and BO values the tests read
dataset stepA table beside the items, for pattern steps and the AImbrec.break_history_book, motif.booking_events, motif.positions
AI toolsQuestions the AI may ask while investigatingcats.trades, motif.trades, mbrec.break_history

Write the data contract first: every field the tests and checks need, and the tool that supplies it. A field no tool supplies yet does not break anything: the tests that need it show "not run", and the capability's "Data and parameters" panel lists it under "Data needed", so the system team knows what to add.

One by one

Building a new capability from a skill

  1. Collect the inputs

    The skill document; the systems involved and the questions each can answer over MCP (the tool list); a few real past cases with the outcome a controller decided; who reviews, who releases, who owns it.

    Who: BA and the skill owner · Output: an inputs page in Confluence

  2. Sort the skill into the four kinds

    Go section by section, as in the mapping table above. Write each rule as a sentence of the form "fails when …", each judgement as an instruction, each people point as a stop, each open number as a parameter.

    Who: BA with a controller · Output: a four-column sheet

  3. Write the data contract

    List every field the rules read, and the MCP tool that supplies it (load, enrich, data set). Mark the gaps and ask the system teams for them.

    Who: BA and the developer · Output: field → tool table

  4. Allow the tools

    Add each system and its tools to connectors.yaml: address, which argument carries the book (so access is checked per person), and access: write on anything that changes a system. Use the stub until the real server is ready.

    Who: developer · Output: connections on the allow-list

  5. Create the capability (the shape)

    Authoring → guided form, or a YAML file: what one case is, how items load, the step list, where a person stops (and the question they answer), who reviews, and what teams may change.

    Who: developer · Output: capability draft

  6. Create the team's group

    When cases open (an event or a schedule), when they are due, enrich, and the thresholds left empty until confirmed.

    Who: developer with the BA · Output: group draft

  7. Write the playbook

    Scenario checks first, then cause checks; the tests with what fails them, the data they need, and whether they block a POST; the categories (deterministic or judgement, owning team); the verdict table by side; guards such as "an FO cause never posts".

    Who: BA and a controller · Output: the rules, in the group

  8. Write the AI's part, and only that

    Instructions for the judgement cases only, telling it what the playbook has already done; the tools it may use; the output sections it must fill; specialists for long trawls.

    Who: skill owner and developer · Output: AI instructions and tools

  9. Set the people points

    The question at the stop before the AI; reviewer roles; the completion checklist; which verdicts need a tick and words; who may be asked for evidence; which decisions raise a ticket and for whom.

    Who: controller lead · Output: review set-up

  10. Check

    Click Check (or run it on the file). It refuses anything inconsistent and says why: a step that needs data nothing earlier made, a tool not on the allow-list ("…is not an onboarded connector tool"), a team setting the capability has no step for.

    Who: developer · Output: no problems listed

  11. Run it on test data, then evaluate

    Run a case on a test book and walk it as a controller. Then replay the past cases from step 1 (and the skill's worked example): AOF shows how often it agrees with what the controller decided, and where it differs.

    Who: controllers and QA · Output: agreement figure and a differences list

  12. Version, approve, and keep improving

    Save a version; a second owner approves it; new cases use it. Each week, look at the novel breaks and the judgement calls approved unchanged five times: they are the next rules.

    Who: owner · Output: live version; next rules

Starter

A minimal capability and group that pass Check

Set up for real: example/ takes a slightly bigger slice (six checks, three tests) through every step on an empty AOF: submit, four eyes, approve, the group, a case, the tollgate, review and sign-off, with the real outputs, console screenshots and a script that repeats it against any AOF.

A price-break version of FOBO, cut down to one check and one test, to copy and grow. Both files were run through AOF's own checks: no problems. A first draft forgot the enrich step, and Check answered: "enrich is set but the workflow has no enrich step".

capability.yaml: the shape
id: price.break.investigation
name: Price break investigation
description: Investigate price breaks a reconciliation has found; explain each, settle what the playbook can, a controller signs off.
owners: { people: [erin], role: AOF_RECON_OWNER, four_eyes: true }
case:
  label: Price break run
  item_label: Break
  key: [book, cob]
  subject: "{book} · COB {cob}"
  scopes: { book: book }
items:
  load: { tool: mbrec.breaks, args: { book: $case.book, cob: $case.cob } }
  id_field: instrument
  amount_field: difference
  display: [instrument, desk, break_type, difference]
steps: [load, enrich, classify, group, reason, draft, validate, review, record]
pause_before: [reason, review]
tollgates:
  reason:
    check: Are these today's breaks, and is the playbook's classification right?
group_by: [break_type]
reasoning:
  reasoner: llm
  output: verdict
  tools: [mbrec.break_history]
  skill: |
    You investigate price breaks. Cite only figures from the tools or the breaks.
review: { roles: [FOBO_CONTROLLER], require_comment: [reject, escalated] }
configurable: [case.opens_on, case.due, items, enrich, policy.*, playbook, group_by, group_label, reasoning.skill, reasoning.tools, reasoning.sections, review.roles, review.checklist, requests]
group.yaml: one team's rules
group: price-prime
name: Price breaks — Prime
owners: { people: [frank], role: AOF_FOBO_RECON_OWNER, four_eyes: true }
set:
  enrich:
    - { tool: motif.break_snapshots, args: { book: $case.book, cob: $case.cob }, keys: [instrument] }
  policy:
    mtm_market_movement_tolerance: { value: null, unit: GBP }
  playbook:
    checks:
      - { id: R5, when: "book_status != 'Complete'", category: W, side: UNKNOWN, reason: "Book is {book_status}; start only on complete books" }
    tests:
      - { id: FO-2, side: FO, validates: Price, check: "Yesterday close price = today open price",
          fails_when: "fo_prev_close_price != fo_open_price", needs: [fo_prev_close_price, fo_open_price],
          evidence: [Pricing file], on_fail: "Hold adjustment; raise market-data DQ", blocks_post: true }
    categories:
      A: { name: Price break, determinism: deterministic, escalate_to: Market data }
      H: { name: Novel break, determinism: judgement, escalate_to: Product Control }
      W: { name: Books not complete, determinism: deterministic, escalate_to: Operations, any_side: true }
    default_category: H
    sides: [FO, BO]
    verdicts:
      A: { FO: DO_NOT_POST, BO: POST }
      H: { FO: ESCALATE, BO: ESCALATE }
      W: { FO: ESCALATE, BO: ESCALATE }
    guards:
      - { verdict: POST, when: "side == 'FO'", instead: ESCALATE, reason: "R2: a cause in FO never posts" }
    blocked_verdict: ESCALATE
    escalate_verdicts: [ESCALATE]
    confirm_verdicts: [POST]
  reasoning:
    sections:
      - { id: root_cause, label: Root cause, required: true, hint: "One clear statement, or say it is not established" }
      - { id: verdict_reason, label: Verdict and why, required: true, hint: "The verdict and the reason" }
  review:
    roles: [FOBO_CONTROLLER]
    checklist:
      - { id: what_checked, label: "What did I check?", prefill: tests }
      - { id: root_cause, label: "What root cause was identified?", prefill: root_cause }

Ready

Before controllers use it

  • Every parameter confirmed by Product Control, or knowingly left empty with the tests that depend on it listed.
  • The data contract complete for the tests that block a POST.
  • The worked example from the skill gives the skill's answer.
  • Agreement with past decisions at or above the agreed level, and every difference explained.
  • The version approved by a second owner.
