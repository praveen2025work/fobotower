A learning guide

Agentic Systems Primer

What an LLM, an agent, a tool, a workflow engine and a knowledge graph each do, and how they fit into one system you can trust.

00

01

The LLM

A large language model predicts the next piece of text, one token at a time. Trained on a vast amount of writing, that simple mechanism produces something that reads, reasons and writes remarkably well.

Strong at

  • Reading messy, unstructured text
  • Summarising and explaining
  • Classifying against described categories
  • Weighing competing explanations
  • Drafting in a required format
  • Deciding what to look up next

Weak at

  • Exact arithmetic over many rows
  • Knowing your private data or today's facts
  • Giving the same answer every run
  • Remembering anything outside its context
  • Reliably enforcing rules on itself
  • Saying "I don't know" unprompted

Five ideas that explain most of its behaviour

IdeaWhat it means in practice
Context windowEverything the model knows for this call: instructions, data, conversation so far. If a fact is not in the window, the model does not have it.
TokensText is billed and processed in tokens (roughly ¾ of a word). More context means more cost and more latency.
Non-determinismThe same question can produce different wording or even different conclusions. Design for that; don't assume replay gives the same answer.
HallucinationWhen information is missing, the model can produce something plausible and wrong. Grounding it in retrieved facts is the main defence.
Structured outputYou can require the answer to match a JSON schema (fields, allowed values), so code can check it instead of parsing prose.
Use the LLM for judgement. Get facts from data and rules from code.
In the FOBO project

Break categories A–F are settled by rules in code. Only G (corporate action) and H (novel) are "judgement" categories that go to the model. The model must answer in the SkillVerdict schema.

02

Agents and harnesses

A plain LLM call is one question and one answer. An agent is an LLM running in a loop, choosing actions until it can answer.

ThinkWhat do I know? What do I need?
ActCall a tool, e.g. fetch evidence
ObserveRead the tool's result
Repeat or answerLoop until confident, then conclude

The model decides which tool to call and when to stop. That flexibility is the point, and also the risk.

The harness

The model alone cannot run a loop, call a database or remember a conversation. A harness is the software around it that does:

  • Runs the loop: sends the prompt, executes the tool calls the model asks for, feeds results back.
  • Gives it tools: an allow-list of what it may call.
  • Loads skills: packaged instructions for a task, kept as files instead of pasted into every prompt.
  • Keeps the session: the running history, so a follow-up question continues where the last one left off.
  • Enforces limits: maximum turns, timeouts, output schema, cost.
  • Logs: every tool call and token count.

Examples: the Claude Agent SDK, the OpenAI Agents SDK, and LangGraph's own prebuilt agent. Many firms run an internal harness as a shared service.

Workflow or agent?

This is the most important design choice. Anthropic's guide Building effective agents draws the same line.

WorkflowAgent
Who picks the pathYour codeThe model
PredictabilityHigh: same steps every timeLower: path varies
AuditEasy: fixed, named stepsNeeds full tool-call logs
Best forKnown proceduresOpen-ended investigation
Build the process as a workflow, and put an agent inside the one step that needs open-ended judgement.
In the FOBO project

The harness runs one session per L4 rec (Rates, Prime, FI Credit…) per business day. The session loads the fobo-investigation skill, uses MCP tools to look things up, and returns a verdict per pattern. Ask Agent One can continue the same session for follow-up questions.

03

Tools and MCP

A tool is a function the model may ask to run. The model never touches your systems directly; it asks, the harness runs the tool, and the result comes back as text.

Each tool is described to the model by a name, a plain-language description and an input schema:

{
  "name": "evidence_required",
  "description": "List the evidence a playbook test needs before it can conclude.",
  "input_schema": {
    "type": "object",
    "properties": { "test_id": { "type": "string", "description": "e.g. FO-6" } },
    "required": ["test_id"]
  }
}

The model reads the description to decide when the tool is useful, so good descriptions matter as much as good code.

MCP, the Model Context Protocol

MCP is an open standard, introduced by Anthropic in 2024, for exposing tools (and read-only resources and prompt templates) to any AI client. You build an MCP server once in front of a system; any MCP-capable harness can connect to it as a client. It runs locally over stdio or remotely over HTTP.

Agent (harness)→ MCP →MCP server→Graph · database · APIs
  • Reuse: one server serves every agent and model.
  • Control: the server decides what is exposed, checks the token, and can enforce entitlements.
  • Audit: every call is a logged request with inputs and outputs.
In the FOBO project

Six planned tools (fobo_list_tests, fobo_evidence_required, fobo_similar_breaks, fobo_book_context…) put the knowledge graph in front of the agent. The console's MCP data panel shows each lookup with its request and rows. The server itself is not built yet.

04

LangGraph

LangGraph is an open-source Python and JavaScript library for building stateful, multi-step workflows and agents. You describe the process as a graph of steps; it runs them, saves state after each one, and can pause for a person.

The six concepts

ConceptMeaning
StateOne typed record shared by all steps: the case file.
NodeA step. A function that reads state and returns updates. It can call code, a database or an LLM.
Edge"After this step, run that one."
Conditional edgeA branch decided by a function: "if anything is unexplained, go to the agent; otherwise go to review."
CheckpointerSaves the state after every step (in memory, SQLite or Postgres). This is what makes runs resumable and auditable.
InterruptPause before or inside a step and wait, for seconds or days, until someone resumes the run with their input.
Gather→Reason by rules→Agent (only if needed)→Pause: review→Post

A minimal example

from typing import TypedDict
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import MemorySaver

class State(TypedDict, total=False):
    breaks: list
    verdicts: dict
    approved: bool

def gather(state):  return {"breaks": load_breaks()}
def reason(state):  return {"verdicts": apply_rules(state["breaks"])}
def agent(state):   return {"verdicts": ask_agent(state["verdicts"])}
def review(state):  return {}
def post(state):    return post_if_approved(state)

def route(state):
    unsettled = [v for v in state["verdicts"].values() if v == "UNKNOWN"]
    return "agent" if unsettled else "review"

g = StateGraph(State)
for name, fn in [("gather", gather), ("reason", reason), ("agent", agent),
                 ("review", review), ("post", post)]:
    g.add_node(name, fn)
g.add_edge(START, "gather")
g.add_edge("gather", "reason")
g.add_conditional_edges("reason", route, {"agent": "agent", "review": "review"})
g.add_edge("agent", "review")
g.add_edge("review", "post")
g.add_edge("post", END)

app = g.compile(checkpointer=MemorySaver(), interrupt_before=["review"])
run = {"configurable": {"thread_id": "prime-2026-08-03"}}

app.invoke({}, run)                          # runs until the pause
# ... hours or days later, after a controller approves:
app.update_state(run, {"approved": True})
app.invoke(None, run)                        # resumes from the saved checkpoint

In production the MemorySaver is replaced by a database checkpointer (for example langgraph-checkpoint-postgres) so paused runs survive restarts.

What LangGraph is not

  • Not an LLM. It calls one when a step needs it; a graph can run with no LLM at all.
  • Not a database, although it stores its checkpoints in one.
  • Not a knowledge graph. The word "graph" here means a flowchart of steps, not a network of data.

Alternatives by need: plain code (a short script with no pauses), Temporal (durable enterprise workflows in many languages), Airflow or Prefect (scheduled batch pipelines), CrewAI or AutoGen (multi-agent conversations).

In the FOBO project

Steps: resolve → gather → group → reason → rank → draft → validate → pause → review → record. Checkpoints live in Postgres. The console's Graph run panel replays them; the Workflow tab edits the step order under four-eyes approval.

05

Knowledge graphs

A knowledge graph stores facts as things (nodes) and the relationships between them (edges), each with properties. It answers "how is this connected to that?"

Book PRIME-MB-05— BELONGS_TO →Desk APAC-CASH

One fact: a node, an edge type, another node. Properties can sit on both, such as the date range the link is valid for.

Key ideas

IdeaMeaning
OntologyThe vocabulary: which node types and relationships are allowed (Book, Desk, BELONGS_TO…). The graph's schema.
TraversalFollowing edges hop by hop: book → desk → legal entity → region.
BitemporalTwo time axes: when a fact was true in the world, and when the system recorded it. Lets you ask "what did we believe on that date?"
Rules as dataRule chains stored as edges (test → finding → category → verdict) so changing a rule means changing data, not code or prompts.

Three ways to store one

OptionQuery languageChoose when
Relational tables (node + edge in Postgres)SQL, recursive CTEsSmall or shallow graphs; you want one database
Property graph database (Neo4j, Neptune, Memgraph)Cypher / GremlinDeep or variable-depth paths, large graphs, graph algorithms
RDF triple store (GraphDB, Stardog)SPARQLFormal ontologies, standards, data shared across organisations

The same question in SQL and in Cypher

"Walk from test FO-3 to its default verdict."

-- Postgres
WITH RECURSIVE walk AS (
  SELECT node_id, 0 AS depth FROM node WHERE node_id = 'test:FO-3'
  UNION ALL
  SELECT e.to_node_id, w.depth + 1
  FROM walk w JOIN edge e ON e.from_node_id = w.node_id
  WHERE w.depth < 5
)
SELECT * FROM walk;
// Neo4j
MATCH (:Test {key:'FO-3'})-[:ON_FAIL_REQUIRES]->(:Test)-[:HAS_FINDING]->(:Finding)
      -[:INDICATES]->(:Category)-[:DEFAULT_VERDICT]->(v:Verdict)
RETURN v

When to switch storage

The number of hops a query walks matters more than the total size. If each node links to 10 others, 2 hops touch about 100 rows and 6 hops about a million.

EdgesHops per queryChoose
Under 1 million1–3Relational is fine
1–50 million4–6 or unknown depthTest both
Any size6+, all paths, graph algorithmsGraph database
In the FOBO project

103 nodes and 67 edges in two Postgres tables. Sources: the playbook YAML (rules), seed data for books and desks (a reference-data feed in production), and the Record step (each day's decisions). PRIME-MB-05 moved from APAC-TREASURY to APAC-CASH on 1 July 2026: two edge rows with date ranges, nothing overwritten.

06

Embeddings and RAG

An embedding turns text into a list of numbers so that similar meanings sit close together. It finds things that are alike, where a graph finds things that are connected.

QuestionBest tool
"Give me break B-7."Table lookup (exact)
"Which desk owns this book on 3 August?"Knowledge graph (connected)
"Have we seen a break like this before?"Vector search (similar)
"Is this break a timing issue or a booking error?"LLM (judgement)

RAG and GraphRAG

Retrieval-augmented generation means fetching relevant facts first and putting them in the model's context, so it answers from evidence instead of memory. GraphRAG does the fetching by walking relationships in a knowledge graph, which is better when the answer depends on how things connect. With tools, the agent does its own retrieval, step by step, as it reasons.

In the FOBO project

A break_embedding table (pgvector) powers "similar past breaks", shown as similar_breaks in the MCP data panel: e.g. break B-1 had 4 similar priors, all 4 approved.

One request, end to end

Follow one case through every layer. The same shape fits reconciliation, claims, KYC reviews or incident triage.

StepWhat happensWho does it
1. TriggerAn event says the data is ready.Source system
2. ResolvePin each item to the right entity and date.Orchestrator step → knowledge graph
3. GatherPull numbers, run checks, look up lineage and history.Orchestrator step → data, graph, vectors
4. RulesSettle everything a written rule can settle.Orchestrator step → rules in the graph
5. JudgementSend what is left to the agent; it investigates with tools.Agent via harness and MCP
6. GuardCheck the agent's answer against hard rules.Code
7. PauseShow the draft with evidence; wait for a person.Orchestrator interrupt → interface
8. Act and recordCarry out the approved action; save the outcome as tomorrow's history.Orchestrator step → database, graph
Facts from data. Rules from the graph and code. Order from the orchestrator. Judgement from the LLM. Decisions from people.
08

Guardrails

In regulated work the controls around the model matter as much as the model. These are the usual ones.

ControlWhat it prevents
Output schemaFree-text answers code cannot check; missing fields; invented verdict values.
Guards in codeThe model overruling a hard rule ("an FO-side cause never posts").
Human approvalAny irreversible action taken without a person's sign-off.
Least-privilege toolsThe agent reading or changing more than the task needs.
Audit trail"Why did it decide that?" going unanswered. Keep checkpoints and every tool call.
Fail to a personGuessing when data is missing. Escalate instead.
VersioningSilent changes. Version prompts, skills, rules and workflows; record which version each run used.
EvaluationsQuality drifting unnoticed. Re-run a fixed set of known cases on every change.
IdempotencyA double-click posting twice. One key per decision.

Which tool when

If you need to…Reach for
Read, summarise or judge unstructured informationAn LLM
Investigate where the next step depends on what you findAn agent in a harness
Let any agent query your systems safelyAn MCP server
Run a fixed procedure with steps, branches and pausesA workflow engine such as LangGraph
Wait days for a human and resume exactlyCheckpointing and interrupts
Answer "how is this connected?"A knowledge graph
Answer "what is this similar to?"Embeddings and vector search
Answer "give me exactly this record"A regular table and SQL
Guarantee a rule is always followedCode, not a prompt

Glossary

Agent
An LLM running in a loop that chooses actions (tool calls) until it can answer.
Checkpoint
A saved copy of a workflow's state after a step. Enables resume, replay and audit.
Context window
All the text a model can see in one call.
Cypher
Neo4j's query language, written as patterns of nodes and arrows.
Edge
Two meanings. In LangGraph: the link between two steps. In a knowledge graph: a relationship between two things.
Embedding
A list of numbers representing meaning; close vectors mean similar content.
Evaluation (eval)
A fixed set of test cases used to measure an AI system's quality over time.
GraphRAG
Retrieval that follows relationships in a knowledge graph before prompting the model.
Hallucination
A confident, plausible and wrong model output.
Harness
The software that runs an agent: loop, tools, skills, session, limits, logs.
Human in the loop
A person reviews or approves before the system acts.
Idempotency
Doing the same action twice has the same effect as doing it once.
Interrupt
A deliberate pause in a workflow that waits for outside input.
MCP
Model Context Protocol: an open standard for exposing tools and data to AI clients.
Node
Two meanings. In LangGraph: a step. In a knowledge graph: a thing (book, desk, rule).
Ontology
The allowed types of things and relationships in a knowledge graph.
RAG
Retrieval-augmented generation: fetch facts, then let the model answer from them.
Session
A conversation with an agent that keeps its history, so later turns build on earlier ones.
Skill
Packaged instructions for a task, loaded by the harness as a file.
SPARQL
The query language for RDF triple stores.
State
The shared record a workflow's steps read and update.
Structured output
A model answer forced to match a JSON schema.
Token
The unit of text a model reads and writes, roughly ¾ of a word.
Tool
A described function the model may ask the harness to run.
Workflow
A process whose steps and order are defined in code, not chosen by the model.
11

Check yourself

Answer each in your head, then open it.

If the LLM can do the analysis, why do we need LangGraph?

The LLM supplies judgement for one step. LangGraph runs the whole procedure around it: fixed order, rules first, pausing for days until a person approves, resuming exactly, and keeping a checkpoint of every step for audit. An LLM call cannot wait, cannot enforce rules on itself, and forgets everything after the call.

Could Neo4j replace LangGraph?

No. Neo4j stores connected data; LangGraph runs steps. They share the word "graph" but do different jobs. Neo4j could replace where the knowledge graph is stored.

Where should "an FO-side cause never posts" live: in the prompt or in code?

In code (and as data in the rulebook), applied after the model answers. A prompt can ask the model to follow a rule; only code can guarantee it.

A controller asks a follow-up question the next morning. What keeps the agent from starting cold?

The harness session. The orchestrator saved the session id in its state, so the chat can continue the same session with the earlier analysis in context.

"Have we seen this before?" versus "Who owns this book?": which store answers each?

The first is similarity: embeddings and vector search. The second is a relationship on a date: the knowledge graph.

Why send the agent one L4 rec per session instead of one break per session?

Tens of sessions a day instead of thousands, and the agent sees each pattern across all its breaks. It pulls detail through MCP tools when it needs it, and code still checks every break against the guards.
